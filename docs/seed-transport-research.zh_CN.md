# 固定棋盘压缩与声音传输抗噪调研

调研日期：2026-10-27。目标是浏览器通过扬声器向AI Passport麦克风传送精确的36×32二值棋盘，不要求安装手机应用。
以下是可复现的主机实验和候选方向；已交付固件尚未实现声音接收器。

## 影响设计的结论

| 问题 | 结论 |
| --- | --- |
| 最少数据 | 保留图案来源：共享图案编号或带版本的随机生成规则可以代替整盘数据；任意编辑后的棋盘仍需通用无损编码。 |
| 尺寸固定 | 宽高是协议常量，不传输；原始棋盘恰好1152bit，即144字节。 |
| 通用压缩 | 比较裁剪位图、稀疏／组合数位置编码和熵编码，计入元数据；保留144字节位图作为上限。 |
| 抗噪 | 同步、内层纠错、CRC验证短帧、丢帧恢复和循环重播一起使用；CRC本身不能修复数据。 |
| 内存 | 所测配置下ggwave可变长接收约需4MiB缓冲，应使用固定短帧和仅接收模式。 |
| 使用时间 | 优化完整验证成功所需的期望时间，包含帧补齐、冗余和重试，而不只比较载荷字节数。 |

## 对固定1152bit棋盘做压缩

棋盘共有`2^1152`种状态，无损编码不可能让所有状态都短于1152bit。
已知密度和空间结构可以减少典型数据量；双方共享生成规则时还能进一步减少。

协议共同固定36×32、B3/S23及格子遍历顺序。种子只包含生死位，细胞年龄配色、计数器和界面状态保留在本地；
边界和播放速度只需要少量控制位。

| 表示 | 发送内容 | 适用条件与要求 |
| --- | --- | --- |
| 共享图案 | 图案编号；必要时加位置、变换和代数 | 居中固定预设的内容编号可为1字节，需固定图案表版本。 |
| 随机规则 | PRNG标识／版本、种子号和密度 | 随字段宽度约6～12字节内容；双方PRNG、位序和零种子行为必须完全一致。手工编辑后不能继续使用该规则代替棋盘。 |
| 图案加代数 | 初始图案编号和有上限的代数 | 使用相同尺寸、规则和边界演化重建；限制重建时间，并验证重建棋盘。 |
| 裁剪位图 | 子矩形位置／范围及位图 | 本原型把裁剪头压入22bit、3字节；它描述子区域，不是重复发送已经确定的整盘尺寸。 |
| 稀疏位置 | 活／死细胞数量及11bit格子编号 | 适合零散稀疏细胞，选择数量较少的一类。 |
| 枚举编码 | 数量`k`及该排列在`C(1152,k)`种状态中的编号 | 编号占`ceil(log2(C(1152,k)))`bit，另加数量／模式；主机原型已精确往返，多精度运算成本需在设备上测量。 |
| Range／ANS | 固定或随包发送的概率模型和二值码流 | 可使用左格、上格作为上下文，计入概率表、结束状态和字对齐补齐。 |
| DEFLATE | raw DEFLATE码流 | 使用标准库作为参考；部分结构化图案有效，但144字节小对象不一定适合通用压缩。 |

枚举编码是对受约束二进制序列编号的经典方法，参见Cover的[原始论文](https://isl.stanford.edu/~cover/papers/transIT/0073cove.pdf)。
本实验使用colex顺序的组合数编号和Python精确`math.comb`，不宣称实现论文中特定的lex顺序码流。

### Range与ANS实测

使用[constriction 0.4.2](https://github.com/bamler-lab/constriction/tree/v0.4.2)，对相同713个棋盘的六种熵编码配置分别完成精确往返。
字节数包含库的32bit字对齐和结束状态、1字节模式标识；需要时还包含1字节拟合概率或4字节上下文概率。
整盘宽高仍是协议常量。

| 棋盘或样本组 | 基础候选最小值 | Range拟合密度 | Range左／上上下文 | ANS左／上上下文 |
| --- | ---: | ---: | ---: | ---: |
| R五连块 | 6 | 10 | 9 | 13 |
| 脉冲星 | 26 | 42 | 33 | 33 |
| R五连块第50代 | 48 | 50 | 29 | 33 |
| R五连块第100代 | 29 | 30 | 21 | 25 |
| R五连块第300代 | 25 | 26 | 21 | 21 |
| 28%随机组中位数 | 126 | 126 | 129 | 133 |
| 50%随机组中位数 | 145 | 150 | 149 | 153 |

共享固定28%模型的Range在28%随机组达到125字节中位数，略低于枚举编码，不需要传拟合模型。
空间上下文对结构化演化状态改善更明显，对独立随机信源没有收益；所有编码仍保留原始位图兜底。

概率量化为255种非零字节值；已解码的左格和上格决定四种上下文，首行／首列外部视为0。
双方使用一致的定点模型构造（`perfect=False`），接收端无需保存随包发送的上下文图。
网页与固件必须固定整数CDF构造规则和编码版本；设备解码内存与实时预算尚未测量。

## 抗噪：可以借鉴二维码的哪些能力

DENSO说明了二维码使用Reed–Solomon纠错及增加冗余的取舍。恢复百分比针对码字，不代表图片任意位置或音频任意片段损坏同样百分比就一定能恢复。
参见[DENSO官方说明](https://www.qrcode.com/en/about/error_correction.html)。

| 机制 | 解决的问题 | 成本／边界 |
| --- | --- | --- |
| 前导和导频 | 从循环中途开始、时钟／频率偏移 | 增加时间，在短帧之间重新同步。 |
| 可听频段FSK | 背景噪声中的音调检测 | 频段需按实际麦克风和扬声器选定，超声接收尚未验证。 |
| 内层RS／ECC | 帧内有限数量符号损坏 | 校验越多净速率越低，ggwave已经自带内层ECC。 |
| 每帧CRC | 帧头、分片编号或内容损坏 | 整帧丢弃，转为位置已知的擦除。 |
| 交织 | 连续噪声破坏相邻符号 | 把损坏分散到不同码字，代价是缓冲和延迟。 |
| 外层纠删码 | 整帧丢失或被CRC拒绝 | 从足够数量的有效分片恢复。 |
| 循环重播和去重 | 错过开头、间歇性噪声 | 跨循环保留有效分片，不反复覆盖棋盘。 |
| 对象CRC和有界解码 | 残留损坏或不兼容重建 | 完整校验及实体确认后才应用，CRC不提供身份认证。 |

### 错误与擦除实验

字节错误实验把156字节对象（8字节示例头＋144字节棋盘＋4字节CRC32）加上32字节校验，该实验与后面的分片纠删实验相互独立。

| 损坏模型 | 次数 | 精确恢复 |
| --- | ---: | ---: |
| 16个未知位置错误字节 | 100 | 100 |
| 32个位置已知擦除 | 100 | 100 |
| 8个错误＋16个擦除 | 100 | 100 |
| 17个错误，超过配置界限 | 100 | 0，全部拒绝 |
| 33个擦除，超过配置界限 | 100 | 0，全部拒绝 |

边界是`2*错误数 + 擦除数 <= 校验符号数`。超过边界后不能保证恢复或检测，因此仍需对象级校验。
实验使用[reedsolo 1.7.0](https://pypi.org/project/reedsolo/1.7.0/)。

突发实验使用四个独立39字节块，每块加8字节校验；连续损坏12字节时，未交织布局失败，四路交织布局恢复，总校验量同为32字节。
这个比较只针对这两个短块布局，不表示单个更大的RS块也会被相同突发错误破坏。

分片实验把156字节示例补齐为十个16字节源片，通过逐列RS再生成四个修复片；十四片中任丢四片的**全部1001种组合**均恢复原对象。
这是主机擦除模型，不是麦克风实测，也不宣称其帧格式兼容RFC；MDS纠删原理参见[RFC 5510](https://www.rfc-editor.org/rfc/rfc5510.txt)。

| 独立丢帧模型 | 十个数据帧，播一遍 | 十个数据＋四个修复帧，播一遍 | 十个数据帧，完整播两遍 |
| --- | ---: | ---: | ---: |
| 每帧丢失10% | 34.9% | 99.1% | 90.4% |
| 每帧丢失20% | 10.7% | 87.0% | 66.5% |

此表是二项分布计算；实际房间噪声可能造成相关丢失，仍需交织、重播和实物声学测试。

## ggwave资源与波形测量

固定依赖为[GGWave 060aec73](https://github.com/ggerganov/ggwave/tree/060aec73dd7123ccac200442f75bdc7369795ffe)，MIT许可。
使用公开`prepare(parameters, false)`／`heapSize()`，24kHz、512点FFT、I16麦克风输入、仅接收、DSS及单一协议。
缓冲大小在主机计算，主机对象另占1464字节；未计入任务栈、codec重新开启和集成开销。

| 协议／固定载荷 | 接收堆 | 波形时长 |
| --- | ---: | ---: |
| 可变长 | 4,219,368字节 | 当前内存不可用 |
| DT_FASTEST／8字节 | 31,032字节 | 0.768秒 |
| DT_FASTEST／16字节 | 46,512字节 | 未测 |
| DT_FASTEST／24字节 | 61,992字节 | 2.048秒 |
| DT_FASTEST／32字节 | 80,608字节 | 未测，过于接近最大连续空闲80KiB |
| MT_FASTEST／8字节 | 49,464字节 | 1.536秒 |
| MT_FASTEST／16字节 | 80,304字节 | 未测，集成余量有限 |
| MT_FASTEST／24字节 | 111,144字节 | 4.096秒，超过已记录的约91KiB空闲堆 |

现有音频BSP能读PCM，交付版默认16kHz；候选24kHz格式或重采样路径仍需真机验证时钟和资源。
512/24000对应每块21.33ms，是必须满足的实时预算；主机FFT测试不能证明无硬件浮点的ESP32-C3也能按时完成。

### 模拟信道结果

每项为十个独立帧；噪声也覆盖前后静音，输入量化为16bit PCM，各条件单独测试，没有叠加成最恶劣环境。
检查精确内容并拒绝CRC错误候选；本轮为**640次软件实验，没有实物声学测试**。

| 信道模型 | DT／24B | MT／24B | MT／8B |
| --- | ---: | ---: | ---: |
| 干净信道 | 10/10 | 10/10 | 10/10 |
| 高斯噪声，SNR -15dB | 0/10 | 9/10 | 6/10 |
| 帧内连续500ms静音 | 0/10 | 9/10 | 0/10 |
| 播放加速1% | 0/10 | 10/10 | 10/10 |

小样本用于暴露取舍，不是成功率保证。更长的MT帧消耗更多内存和时间；缩短它可以适配当前内存，但帧头／CRC比例更高。
选定DT配置前需验证频率捕获和采样时钟偏差。

## 候选方向与验收条件

```mermaid
flowchart LR
    A[固定棋盘或带版本生成规则] --> B[选择最小的已支持表示]
    B --> C[对象元数据及CRC]
    C --> D[自适应纠删分片]
    D --> E[帧头及CRC]
    E --> F[内层纠错及可听波形]
    F --> G[麦克风短帧解码]
    G --> H[校验帧并收集分片]
    H --> I[恢复、解码和验证对象]
    I --> J[暂停预览及实体确认]
```

图案或规则能精确描述棋盘时优先发描述；其他情况在通用编码与原始位图之间择优，固定编码／模型版本，输出上限1152格。
未知模式、不可能数量和过长重建必须在应用前失败；使用事务编号与对象校验跨循环保留有效分片，覆盖中途加入、更换种子、超时和取消。

示例24字节声音帧可含6字节帧头、16字节分片及2字节帧CRC；156字节稠密对象用十个源帧和四个修复帧，`14 * 2.048 = 28.672秒`，未计帧间隔、同步和重播。
这只是格式与时间示例，不是已定协议；小对象应减少帧数并调整冗余，较慢MT方案需要另算布局。

| 后续验收 | 宣称设备支持前需要的证据 |
| --- | --- |
| 解码资源 | 真机峰值堆、最大连续块、栈、初始化失败处理及每块耗时，保留运行余量。 |
| 浏览器播放 | iPhone／Safari、Android／Chrome、实际采样率、音量、循环间隙和扬声器频响。 |
| 声学信道 | 约定距离、角度和噪声下重复测试，含说话、音乐、削波、突发干扰和漂移，记录校验成功时间及失败。 |
| 完整性与生命周期 | 无效／不完整输入不改棋盘，不混合事务；明确取消／超时，录音与任务完整停止。 |
| 交互 | 进入接收、显示进度／错误、完整校验后暂停预览、实体应用／取消，不要求安装手机应用。 |

## 复现与数据

[数据文件](research-data/seed-sizes.json)由[`tools/research`](../tools/research)脚本生成，不是手填成功表。
Python依赖固定在[`requirements.txt`](../tools/research/requirements.txt)。

```sh
python3 -m venv work/research-venv
export PYTHONPYCACHEPREFIX="$PWD/work/research-pycache"
work/research-venv/bin/python -m pip install -r tools/research/requirements.txt
work/research-venv/bin/python tools/research/seed_sizes.py
work/research-venv/bin/python tools/research/entropy_trials.py
work/research-venv/bin/python tools/research/fec_trials.py
git clone https://github.com/ggerganov/ggwave.git work/research-ggwave
git -C work/research-ggwave switch --detach 060aec73dd7123ccac200442f75bdc7369795ffe
cmake -S tools/research -B work/research-native -DGGWAVE_ROOT="$PWD/work/research-ggwave" -DCMAKE_BUILD_TYPE=Release
cmake --build work/research-native --parallel 4
work/research-native/ggwave_memory
work/research-venv/bin/python tools/research/acoustic_trials.py --library work/research-native/ggwave/src/libggwave.dylib
work/research-venv/bin/python tools/research/acoustic_trials.py --library work/research-native/ggwave/src/libggwave.dylib --payload 8 --output work/research/acoustic-trials-8.json
```

下载、原生构建和音频缓冲均在已忽略的`work/`中。
